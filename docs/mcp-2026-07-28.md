## 1. What changed in 2026-07-28

Sessions **still exist**. What disappeared was not the "client on the wire,"
but the **transport cookie**: the `Mcp-Session-Id` header that the server
issued during `initialize`. In 2026, the same association is established
explicitly (SEP-2567 / SEP-2575).

| Why a session is needed | How it was established in 2025-11-25 | How it is established in 2026-07-28 |
| ----------------------- | ------------------------------------ | ----------------------------------- |
| Client identity | `clientInfo` once in `initialize` | `_meta.clientInfo` + `clientCapabilities` **on every** RPC |
| Principal | Bearer JWT (`client_id`) — vmcp already works this way | Same |
| Live push channel | GET `/mcp` with `Mcp-Session-Id` | POST `subscriptions/listen`; stream ID = request JSON-RPC `id` → `subscriptionId` |
| State across tool calls (basket, browser) | Implicitly in the session | Explicit handle in arguments (`basket_id`) — a pattern, not a new RPC |
| Long-running work | `taskId` (SEP-1686) | `taskId` in the tasks extension |
| Elicitation correlation | In flight within the session | MRTR `requestState` / retry of the same method |
| Resuming interrupted SSE | `Last-Event-ID` | Not supported: the client **reopens** the listen stream / sends a new request ID |

The protocol is sessionless at the HTTP layer. For operators and agents, the
session still exists as an object; it is opened through a different RPC, not
through a header after the handshake.

The nine major changelog items:

1. **No `Mcp-Session-Id` header.** List methods do not depend on the
   connection. Cross-call state uses explicit handles in tool arguments
   (SEP-2567).
2. **No `initialize` / `initialized`.** Every request carries the version and
   client capabilities in `_meta`. A version mismatch produces
   `UnsupportedProtocolVersionError` (SEP-2575).
3. **`server/discover` is required** on the server. A client can call it
   beforehand or use it as a probe over stdio.
4. **GET SSE + `resources/subscribe` have been replaced** by
   `subscriptions/listen` (a single POST stream). Progress remains on the
   response stream of the original request.
5. **Removed:** `ping`, `logging/setLevel`, and
   `notifications/roots/list_changed`. The log level is set through
   per-request `_meta.logLevel`.
6. **Tasks moved to the extension** `io.modelcontextprotocol/tasks`
   (SEP-2663): poll `tasks/get`, use `tasks/update`, with no `tasks/list` and
   no blocking `tasks/result`.
7. **MRTR** replaces server-initiated RPCs (`elicitation/create`, `sampling`,
   `roots/list`): the server returns `resultType: "input_required"`, and the
   client retries the original method with `inputResponses` (SEP-2322).
8. Every result requires **`resultType`**.
9. **No SSE resume** (`Last-Event-ID`). A broken stream loses in-flight state;
   the client sends a new request ID.

The revision also requires the `Mcp-Method` / `Mcp-Name` HTTP headers
(SEP-2243) and the `ttlMs`/`cacheScope` cache hints (SEP-2549), and deprecates
DCR in favor of CIMD.

Deprecated but still present in the specification: Roots, Sampling, and
Logging (SEP-2577).

## 2. Assessment of the official documentation and skill

The `/docs/2026-07-28` page is a solid index covering architecture,
Streamable HTTP, discover, MRTR, tasks as an extension, and Inspector protocol
eras. For this gate, **specification/** matters more than the "build a weather
server" tutorial.

The `mcp-server-dev` plugin that the documentation instructs users to download
**has not caught up with the 2025-11-25→2026-07-28 transition**:

| In the skill | 2026-07-28 reality |
| ------------ | ------------------ |
| `versions.md`: pinned to "MCP spec 2025-11-25," verified 2026-03 | The current revision is `2026-07-28` |
| `elicitation.md`: `server.elicitInput()` / `ctx.elicit()` | Replaced by MRTR |
| `server-capabilities.md`: sampling / roots / logging as "near-free wins" | Deprecated; do not add them |
| Scaffolds use Express/FastMCP/`initialize` | The modern path is stateless + `server/discover` |
| Auth: CIMD SHOULD, DCR MAY (2025-11-25) | DCR is **Deprecated**; CIMD is preferred |

Conclusion: the skill is useful as a **product** guide (remote HTTP vs MCPB,
tool patterns, CIMD). It is not suitable as the protocol contract for vmcp,
hence the `mcp-2026-07-28` overlay.

## 3. Where vmcp stands today

The gateway has two roles: it is an **MCP server** for hosts (`/mcp`,
`/mcp-proxy`) and an **MCP client** for upstreams (stdio + Streamable HTTP).

| Layer | Status |
| ----- | ------ |
| SDK | The vendored `rmcp` **3.1.0** already knows `2026-07-28` (discover, SEP-2243, MRTR types, tasks extension, `legacy_session_mode`). |
| Default version | `ProtocolVersion::LATEST` in rmcp is **`2025-11-25`**, not 2026-07-28. |
| HTTP ingress | `StreamableHttpServerConfig::default()` → `legacy_session_mode: true` + `LocalSessionManager`. |
| Tests | `initialize` + `Mcp-Session-Id` + `2025-11-25` / `2025-03-26`. |
| "Session" product surface | Admin Sessions, JSONL recorder, otel, idle GC, orphan-`initialize` capture. |
| Resume | A local rmcp patch for `Last-Event-ID` ([#2](https://github.com/hewimetall/vmcp/issues/2)) — a feature **removed** in 2026-07-28. |
| Notifications | `on_initialized` inserts a `Peer` into the map and fans out `list_changed`. |
| Tasks | The code is already closer to SEP-2663 (`get_task` / `update_task` stub / extension ID); the **documentation and messages** still describe SEP-1686 (`tasks/result`, `tasks/list`). |
| Auth | A complete DCR AS; vmcp is **not** a CIMD authorization server. The Authentik path already avoids DCR. |
| GraphQL `query_graphql` | Almost orthogonal to the protocol version. |

In short: **the SDK is ahead of the application.** Passing this gate is not a
crate bump; it requires changing the product's session model and supporting
both protocols across a mixed upstream fleet.

## 4. Why this is hard (and not obvious from rmcp)

The intuition that "rmcp 3.1 already speaks 2026, so the gate is almost ready"
is correct **only for the JSON-RPC types**. `VmcpServer` and `ProxyServer`
both implement `supported_protocol_versions` via
`advertised_protocol_versions`, using their `latest` setting: by default,
they advertise legacy revisions through `2025-11-25`, while
`[mcp].latest=true` also advertises `2026-07-28`. The default `ServerHandler`
provides `server/discover`.
`tools/call` / `query_graphql` over a single POST without a session will
probably already work.

The real difficulty is that **the application assumes every client has a
session**. The 2026 protocol forbids that assumption. Sessions cannot simply
be disabled either, because Cursor and our tests still use the handshake.

The sections below describe what happens **today**, without any migration
code, when a modern client connects to `/mcp`.

### 4.1 The recorder and Sessions tab go blank

`capture_mcp` gets its recording key from the `Mcp-Session-Id` header. The
first `initialize` request has no header, so the middleware **waits** for the
ID in the response and backfills it; otherwise, the C2S exchange is
**dropped**:

```67:122:crates/vmcp/src/mcp_capture.rs
    // The very first request ("initialize") arrives WITHOUT an `Mcp-Session-Id`
    // header; rmcp generates the id and returns it in the response.
    // ...
            tracing::warn!(
                method = ?req_method,
                "C2S exchange has no session id (initialize failed or broken client); dropping"
            );
```

A 2026-07-28 client **never** sends or receives `Mcp-Session-Id`. Every
`tools/call` takes this branch. `Recorder::record` is also silent without a
`(client_id, session_id)` pair:

```122:128:crates/vmcp-server/src/recorder.rs
        let Some(cid) = ex.client_id.clone() else {
            return;
        };
        let Some(sid) = ex.session_id.clone() else {
            return;
        };
```

The operational result is that external GraphQL calls work, but the
**Sessions tab, compare view, and JSONL dump remain empty** until the key is
remapped. This does not mean "inventing sessions again." In 2026, identifiers
are already available on the first POST:

- Bearer `client_id` (which vmcp already has);
- `_meta.clientInfo`;
- for the live channel, `subscriptionId` (= the JSON-RPC ID of
  `subscriptions/listen`).

Fixing the recorder means **changing where the sid comes from** and removing
the "wait for the header from initialize" dance. The Admin UI can remain
client → sessions → dump. Under dual-protocol operation, two paths populate
the same tab (cookie vs `_meta`/listen).

### 4.2 Push `tools/list_changed` does not reach a modern client

The current chain is:

1. An upstream (postgres) sends `notifications/tools/list_changed`.
2. `ForwardingClient` puts it on the in-process bus.
3. The forwarder iterates over `peers: DashMap<u64, Peer<RoleServer>>`.
4. The map is populated **only** in `on_initialized`.

```97:99:crates/vmcp-server/src/lib.rs
    /// Connected client sessions, captured on `initialized`. The notification
    /// forwarder fans upstream MCP events out to these peers.
    peers: Arc<DashMap<u64, Peer<RoleServer>>>,
```

```604:607:crates/vmcp-server/src/lib.rs
    async fn on_initialized(&self, context: NotificationContext<RoleServer>) {
        let id = self.inner.peer_seq.fetch_add(1, Ordering::Relaxed);
        self.inner.peers.insert(id, context.peer.clone());
    }
```

The 2026 protocol has **no** `notifications/initialized`. The map remains
empty until the client **opens a push session** through
`subscriptions/listen`. This uses the same peer map but a different
registration point: `on_initialized` → listen handler (acknowledge the
`subscriptionId` and send `list_changed` through this SSE stream, not through
GET `/mcp`).

rmcp 3.1 already supports listen at the transport layer; vmcp still inserts a
peer only during the legacy handshake. With two clients on the same `/mcp`
(Cursor 2025 + a 2026 agent), Cursor receives push notifications but the agent
does not until the forwarder is connected to listen.

This remaps the session entry point; it does not require a new bus. The scope
is a legacy GET SSE branch and a modern listen branch in the same forwarder.

### 4.3 CI will stay green and hide the failure

`http_smoke` and almost all integration tests go through
`handler.serve(transport)`:

```187:188:crates/vmcp/tests/common/mod.rs
    let transport = StreamableHttpClientTransport::from_config(config);
    handler.serve(transport).await.expect("MCP handshake")
```

In rmcp 3.1, `ProtocolVersion::LATEST` = **`2025-11-25`**. The test client
performs `initialize` itself, receives `Mcp-Session-Id`, and registers the
peer. The scenarios in sections 4.1–4.2 **are not reproduced in CI**.

The separate raw HTTP tests (`session_survives_rpc_error`,
`session_fd_burst`) **explicitly** send `2025-11-25` and test resume via
`Last-Event-ID`, a feature that 2026 **removes**. Until those tests are
duplicated along the modern path, "migrated to 2026" means a green run against
the old protocol.

### 4.4 Dual protocol: two ways to *open* a session, not "with and without sessions"

`StreamableHttpServerConfig::default()` enables
`legacy_session_mode: true`. This is necessary while Cursor, vmcp-lite, and
scripts open sessions through `initialize`. As a result, one process has two
entry points into the same operator-facing object:

| | 2025-11-25 client | 2026-07-28 client |
| --- | --- | --- |
| How to open it | `initialize` → `Mcp-Session-Id` cookie | First POST with `_meta.clientInfo` (+ Bearer) |
| How to open push | GET `/mcp` with the cookie | POST `subscriptions/listen` → `subscriptionId` |
| Interrupted SSE | `Last-Event-ID` replay (our rmcp patch, issue #2) | Reopen listen / use a new request ID |
| Logs | `logging` capability + `notifications/message` | Only if `_meta` contained `logLevel` |
| Idle GC | `LocalSessionManager::close_session` after the TTL | Close the listen stream; there is no cookie to collect |

Each row is a branch for how the object was opened, not a separate product.
rmcp switches the transport behavior, but the recorder and forwarder still
recognize only the old entry point.

The `third_party/rmcp` patch specifically fixes resume after a JSON-RPC error.
It **must not** apply to 2026, where the specification prohibits redelivery.
The patch cannot be removed while the legacy path remains. Restricting it to
`legacy_session_mode` requires separate care; otherwise, a modern client will
receive prohibited replay.

### 4.5 The gateway is also a client, and upstreams will not migrate in lockstep

`UpstreamPool` retains a `RunningService` after the handshake with a
stdio/HTTP upstream. `ForwardingClient::get_info()` returns the default
capabilities and operates in the world of `on_tool_list_changed` (the old
notifications).

The demo fleet (time, filesystem, presentation) will remain on 2025 for a long
time. An HTTP upstream that enables 2026 will:

- stop sending GET SSE / `resources/subscribe`;
- expect `subscriptions/listen` and `_meta` on every RPC;
- potentially respond to `initialize` with `-32601` or require discover.

The pool currently applies **one** lifecycle to all upstreams. Each upstream
needs its own probe: `server/discover` → fallback `initialize`. Otherwise,
"upgrading vmcp" causes one Notion-like MCP to fail while the others continue
working. This is the client side of the same dual model, not the server side.

### 4.6 Tasks and auth are not a version bump, but they are not free either

The code already calls `get_task` / `cancel_task` and attaches the extension
ID (SEP-2663). The documentation, `instructions`, and GraphQL messages still
say to "poll `tasks/result` / `tasks/list`." `update_task` is a stub (`get`
and nothing else). A 2026 client that sends `tasks/update` for input receives
"ok" with no effect.

DCR does not have to be changed immediately (deprecated ≠ removed), but vmcp
does not implement CIMD as an AS, and Cursor still uses DCR. This is not a
phase-one blocker. It is a separate piece of work if the goal is to "comply
with the specification's SHOULD" rather than merely support its RPCs.

### 4.7 What is *actually* inexpensive

- `query_graphql` itself, the dynamic schema, the registry, and hot reload.
- `server/discover` (provided by rmcp by default).
- The `Mcp-Method` / `Mcp-Name` headers (rmcp validates them for 2026).
- `resultType` (rmcp adds it when the negotiated version is ≥ 2026-07-28).

This is why vmcp appears to be "almost on 2026" from the outside. The tool
call does not break; the **operator control plane and push path** do.

## 5. Migration complexity assessment

**Overall assessment: medium-high (6.5–7 / 10) with dual-protocol support.**
This is not "sessions were removed, so rewrite the product." There are **two
entry points into the same session** (cookie-based `initialize` vs `_meta` +
`subscriptions/listen`) while Cursor remains on 2025. The assessment drops to
5.5 / 10 if legacy support is removed.

The complexity lies in remapping the key and peer registration point, plus the
mixed-version upstream client. Leave GraphQL alone.

| Subsystem | Complexity | Changes |
| --------- | ---------- | ------- |
| Dual protocol on `/mcp` | Medium | rmcp is already dual-stack with `legacy_session_mode=true`, and `[mcp].latest=true` already advertises `2026-07-28` alongside legacy revisions. Add modern stateless smoke tests for `server/discover` + per-request `_meta` + SEP-2243 headers, without `Mcp-Session-Id`. |
| Sessions / admin / recorder / otel | **Medium** | This is not a new object. Sid: cookie **or** `client_id`+`clientInfo` / `subscriptionId`. Remove the orphan-`initialize` wait from `mcp_capture.rs`. |
| Last-Event-ID patch | Medium | Legacy path only. Modern clients reopen listen. |
| Notifications | **Medium-high** | Use the same peer map, but register on `subscriptions/listen`, not `on_initialized`. Keep GET SSE for legacy clients. |
| Upstream pool (client) | **High** | Each upstream needs a `ClientLifecycleMode`: discover → fallback initialize. The fleet is mixed (stdio Python 2025-11-25 + HTTP 2026). `ForwardingClient` currently assumes the session/initialize model. |
| Tasks | Medium | Finish SEP-2663: implement `tasks/update`, remove `tasks/result` from documentation/instructions, and stop advertising `tasks/list`. The SQLite store is almost ready. |
| Auth | Medium | DCR can remain for now (deprecated, not removed). A CIMD AS is separate work. Add `iss` (SEP-2468), `application_type` (SEP-837), and bind credentials to the issuer (SEP-2352). |
| Proxy `/mcp-proxy` | Medium | The same ServerHandler, plus list cache hints. |
| GraphQL aggregation | Low | Internal layer. |
| Tests | High volume | Almost all HTTP integrations depend on the handshake. Add a legacy × modern matrix. |
| Clients (Cursor, vmcp-lite) | External | **Do not** disable legacy while hosts remain on 2025-11-25. |

### What does *not* need to be rewritten from scratch

- GraphQL schema / `query_graphql`
- Registry, sidecars, lock, hot reload
- OAuth consent UX (it can evolve)
- The entire Admin SPA: the Sessions tab remains; only the way its sid is
  established changes

### Primary risk

One process has two ways to **open** the same session: the cookie after
`initialize`, or `_meta` + `subscriptions/listen`. rmcp supports both at the
transport layer. The recorder and forwarder still recognize only the cookie.

The second risk is **upstream translation**. With a 2026 client and a 2025
upstream, the gateway performs `initialize` against the upstream itself and
does not wait for a cookie from the modern client.

## 6. Recommended phases (not estimates in days)

1. **Modern stateless smoke coverage on `/mcp`:** with `[mcp].latest=true`
   already advertising `2026-07-28`, cover `server/discover` and
   `tools/list`/`tools/call` with `_meta` and no cookie. Keep the legacy tests
   working.
2. **Cache hints + `resultType`:** verify that rmcp adds them to list/tool
   results; add them if `list_tools` returns a raw struct without `ttlMs`.
3. **Make `subscriptions/listen` the new push-session entry point:** register
   the peer here, not in `on_initialized`. Keep legacy GET SSE.
4. **Remap the recorder sid:** cookie **or** `client_id`+`clientInfo` /
   `subscriptionId`. Remove the wait for `Mcp-Session-Id` from initialize.
   Keep the same Sessions tab.
5. **Upstream client lifecycle:** probe with `server/discover`, then fall back
   to `initialize`. Do not force 2026 on the stdio demos.
6. **Complete Tasks SEP-2663:** implement `tasks/update`; update the
   documentation and the `query_graphql`/`run_task` instructions.
7. **Auth:** add `iss` and `application_type`; implement the CIMD AS as a
   separate step after dual-protocol support is stable.
8. **Do not remove** the Last-Event-ID patch while legacy_session_mode
   remains enabled.

Phase 1 is a narrow transport slice. Phases 3–5 are the real cost:
notifications, observability, and mixed upstreams.

## 8. Patterns and solutions already used elsewhere

The public designs below address the same problem: one `/mcp`, two protocol
eras, and different ways to establish a session. This is not theoretical;
gateways and SDKs are already built this way.

### 8.1 Dual profile on one path, classified by contract

[Light-Fabric `light-gateway`](https://www.networknt.com/light-fabric/design/mcp-2026-07-28.html)
uses two adapters (legacy stateful / 2026 stateless) and **one** application
core (auth, tools, audit). It chooses a profile by the wire contract, **not**
by the absence of `Mcp-Session-Id`: a missing cookie from a legacy client is a
malformed request, not a modern request.

Its table can be copied almost verbatim for vmcp:

| Condition | Profile |
| --------- | ------- |
| `initialize`, no sid, legacy version | Legacy handshake |
| `Mcp-Session-Id` is present and the request does **not** claim 2026 | Legacy session |
| Both the header **and** `_meta` contain matching `2026-07-28` values | Modern / stateless |
| 2026 + stale `Mcp-Session-Id` | Modern; **ignore** the cookie and do not touch the session store |
| Legacy non-initialize request without a sid | Reject: missing session |
| Version is present only in the header or only in `_meta` | `HeaderMismatch` `-32020` |

Both adapters normalize into a shared context (`session_id` **or**
`Stateless` + `client_info` + `auth`). This is what "establishing a session
differently" means; it does not create two products.

The specification says the same thing: a dual-era server examines **how the
client started** (`initialize` vs `_meta`) and **MAY** serve both eras from the
same endpoint
([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).

### 8.2 Do not advertise capabilities that are not implemented

Light-Fabric explicitly defines the first milestone as `server/discover` +
`tools/list` + `tools/call`. `subscriptions/listen`, MRTR, tasks, and the
backend bridge are separate gates. The capabilities returned by `discover`
must include only what is actually wired; otherwise, a modern client opens
listen and receives silence.

For vmcp, do **not** include the notification/listen capability in modern
`discover` while peers are still attached in `on_initialized`.

### 8.3 The version belongs to the gateway, not the upstream

[AWS AgentCore Gateway](https://aws.amazon.com/blogs/machine-learning/how-agentcore-gateway-supports-the-mcp-2026-07-28-spec/)
puts `supportedVersions` on the gateway, not the target. Its rollout has three
steps: add `2026-07-28` alongside `2025-11-25` → let clients migrate → remove
the old version. The client chooses a version **on every** request through
`MCP-Protocol-Version`. An old client notices no change when using a
dual-version gateway.

Translating between a 2025 client and a 2026 upstream works for ordinary
`tools/call` requests. Elicitation/sampling/MRTR are **not** translated and
produce an error. vmcp is already close to this model: GraphQL/tools do not
depend on the era. Do not promise MRTR until an adapter exists.

### 8.4 Automatic translation + version intersection during federation

[agentgateway / Solo](https://docs.solo.io/agentgateway/latest/mcp/spec-compatibility/)
uses the following behavior:

- new client → new upstream: forward `server/discover`;
- new client → old upstream: transparently fall back to `initialize`;
- old client → new upstream: preserve the handshake;
- multiple upstreams: return the **intersection** of versions to the client.

The proxy **disables** `cacheScope: public`: policy/auth make the catalog
per-principal, so only `private` is valid (as in Light-Fabric).

For push, see [PR #2599](https://github.com/agentgateway/agentgateway/pull/2599):
`subscriptions/listen` fans out to multiple backends, and per-upstream ACKs
produce one downstream ACK. This pattern is ready to apply to the vmcp bus:
client listen → upstream subscriptions → synthesize
`notifications/subscriptions/acknowledged`.

### 8.5 `protocolEra`: `legacy` \| `auto` \| `modern`

[Inspector](https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector/protocol-eras)
and its
[v2 impact note](https://github.com/modelcontextprotocol/inspector/blob/main/specification/v2_new_spec_impact.md)
treat the era as a first-class property orthogonal to the transport. The same
URL can be opened as legacy or modern.

- Do **not** default Debug/recorder to `auto` (a probe pollutes the
  transcript, and legacy stdio hangs).
- Tests **pin** the era instead of accepting "whatever works."
- When modern listen is interrupted, **POST**
  `subscriptions/listen` again rather than using `Last-Event-ID`.
- Modern Tasks poll `tasks/get`, have no `tasks/list`, and provide input
  through `tasks/update`.

For vmcp CI, use a `legacy` × `modern` matrix rather than one
`handler.serve()` with `LATEST=2025-11-25`.

### 8.6 The SDK is already dual-stack (rmcp 3)

The [rust-sdk README](https://github.com/modelcontextprotocol/rust-sdk/) and
[discussion #969](https://github.com/modelcontextprotocol/rust-sdk/discussions/969)
state that 2026 is always stateless and `legacy_session_mode` applies only to
`< 2026`. On the client side, use `allow_stateless` and the discover /
initialize / probe lifecycle. Keep shared state in a `Clone` handle (as
VmcpServer already does).

Do not write a second HTTP server. Put a classifier and envelope around the
existing core.

### 8.7 Gateway-owned backend ≠ protocol session

[SEP-2567](https://modelcontextprotocol.io/seps/2567-sessionless-mcp) says that
gateways which used `Mcp-Session-Id` for sticky routing do not need that key
when an upstream is stateless or state is carried in tool arguments. The
remaining case is HTTP→stdio spawning: correlate by **principal / gateway
cookie**, not by protocol session.

A Light-Fabric non-goal is pooling hidden legacy backend sessions by user ID
for stateless clients.

vmcp is already closer to the correct model: `UpstreamPool` contains
**process-level** stdio/HTTP gateway clients, not one client per Cursor
session. They do not need to be torn down when the cookie disappears. For a
modern frontend, they are an implementation detail of the aggregator. Do not
map each frontend listen stream 1:1 to a new child process.

The gateway does **not** interpret handles such as `basket_id`; they are
ordinary `query_graphql` / `run_task` arguments.

### 8.8 Rename "session" in the product documentation

[AGT ADR 0027](https://microsoft.github.io/agent-governance-toolkit/adr/0027-adopt-dual-stack-migration-for-mcp-2026-07-28/)
keeps `MCPSessionStore` as **application auth/state**, not as a transport
session. Server-side `initialized` becomes a no-op shim. The documentation no
longer presents `Mcp-Session-Id` as the normal lifecycle.

For vmcp, the Sessions tab represents operational correlation (JWT
`client_id` + `clientInfo` / `subscriptionId` / legacy cookie). Keep the UI.

### 8.9 What vmcp should adopt first

0. **The `[mcp].latest` flag (already in the configuration, off by default).**
   Do not advertise `2026-07-28` in `supportedVersions` until the operator
   enables `VMCP_MCP__LATEST=true`. This is dual-era, not modern-only.
1. Put the Light-Fabric classifier **before** `capture_mcp` (otherwise, modern
   traffic is dropped because it has "no sid").
2. Keep the shared core as-is (`query_graphql`, scopes); adapt only the
   envelope (`resultType`, `ttlMs`, `_meta.serverInfo`).
3. With `latest=true`, explicitly set `supportedVersions` to `2025-11-25` +
   `2026-07-28`; follow the AgentCore rollout.
4. Use `cacheScope: private` for list/discover because scopes filter the
   catalog.
5. Do not advertise listen until the forwarder subscribes to
   `subscriptions/listen` (the agentgateway fan-out+ACK pattern).
6. Test `protocolEra=legacy|modern`, as Inspector does.
7. For upstreams, use the rmcp client probe: `discover` → fallback
   `initialize`. Leave the process pool unchanged.
