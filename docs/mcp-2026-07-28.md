## 1. Что изменилось в 2026-07-28 (суть)

Сессии **остались**. Убрали не «клиента на проводе», а **транспортную
cookie**: заголовок `Mcp-Session-Id`, который сервер выдавал на
`initialize`. В 2026 ту же связь заводят явно (SEP-2567 / SEP-2575).

| Зачем сессия | Как заводили в 2025-11-25 | Как заводят в 2026-07-28 |
| ------------ | ------------------------- | ------------------------ |
| Кто клиент | `clientInfo` один раз в `initialize` | `_meta.clientInfo` + `clientCapabilities` **на каждый** RPC |
| Principal | Bearer JWT (`client_id`) — у vmcp уже так | то же |
| Живой push-канал | GET `/mcp` с `Mcp-Session-Id` | POST `subscriptions/listen`; id стрима = JSON-RPC `id` запроса → `subscriptionId` |
| Состояние между tool call (корзина, браузер) | неявно в session | явный handle в аргументах (`basket_id`) — паттерн, не новый RPC |
| Долгая работа | `taskId` (SEP-1686) | `taskId` в extension tasks |
| Корреляция elicitation | in-flight в session | MRTR `requestState` / retry того же метода |
| Resume оборванного SSE | `Last-Event-ID` | нет: клиент **заново** открывает listen / шлёт новый request id |

Протокол sessionless на уровне HTTP. Оператору и агенту сессия как
объект никуда не делась — её открывают другим RPC, не header после
handshake.

Девять major-пунктов changelog:

1. **Нет заголовка `Mcp-Session-Id`.** List-методы не зависят от
   соединения. Кросс-call состояние — явные handle в аргументах
   инструментов (SEP-2567).
2. **Нет `initialize` / `initialized`.** Каждый запрос несёт версию и
   capabilities клиента в `_meta`. Несовпадение версии —
   `UnsupportedProtocolVersionError` (SEP-2575).
3. **`server/discover` обязателен** на сервере. Клиент может вызвать его
   заранее или как probe на stdio.
4. **GET SSE + `resources/subscribe` заменены** на `subscriptions/listen`
   (один POST-stream). Progress остаётся на response-stream исходного запроса.
5. **Удалены** `ping`, `logging/setLevel`, `notifications/roots/list_changed`.
   Уровень лога — per-request `_meta.logLevel`.
6. **Tasks уехали в extension** `io.modelcontextprotocol/tasks` (SEP-2663):
   poll `tasks/get`, `tasks/update`, без `tasks/list` и без блокирующего
   `tasks/result`.
7. **MRTR** вместо server-initiated RPC (`elicitation/create`, `sampling`,
   `roots/list`): сервер возвращает `resultType: "input_required"`, клиент
   ретраит исходный метод с `inputResponses` (SEP-2322).
8. У всех результатов обязателен **`resultType`**.
9. **Нет resume SSE** (`Last-Event-ID`). Оборванный stream = потеря inflight;
   клиент шлёт новый request id.

Плюс обязательные HTTP-заголовки `Mcp-Method` / `Mcp-Name` (SEP-2243),
cache hints `ttlMs`/`cacheScope` (SEP-2549), DCR deprecated в пользу CIMD.

Deprecated, но ещё в спецификации: Roots, Sampling, Logging (SEP-2577).

## 2. Оценка официальных docs / skill

Страница `/docs/2026-07-28` — нормальный индекс: architecture, Streamable HTTP,
discover, MRTR, tasks-as-extension, Inspector protocol-eras. Для gate важнее
**specification/**, чем tutorial «build a weather server».

## 3. Где сейчас стоит vmcp

Роль шлюза двойная: **MCP-сервер** для хостов (`/mcp`, `/mcp-proxy`) и
**MCP-клиент** к upstream (stdio + Streamable HTTP).

| Слой | Состояние |
| ---- | --------- |
| SDK | Vendored `rmcp` **3.1.0** уже знает `2026-07-28` (discover, SEP-2243, MRTR types, tasks extension, `legacy_session_mode`). |
| Default version | `ProtocolVersion::LATEST` в rmcp = **`2025-11-25`**, не 2026-07-28. |
| HTTP ingress | `StreamableHttpServerConfig::default()` → `legacy_session_mode: true` + `LocalSessionManager`. |
| Тесты | `initialize` + `Mcp-Session-Id` + `2025-11-25` / `2025-03-26`. |
| Продукт «сессия» | Admin Sessions, JSONL recorder, otel, idle GC, orphan-`initialize` capture. |
| Resume | Локальный патч rmcp под `Last-Event-ID` ([#2](https://github.com/hewimetall/vmcp/issues/2)) — фича **удалена** из 2026-07-28. |
| Notifications | `on_initialized` кладёт `Peer` в map и fan-out `list_changed`. |
| Tasks | Код уже ближе к SEP-2663 (`get_task` / `update_task` stub / extension id); **доки и тексты** всё ещё SEP-1686 (`tasks/result`, `tasks/list`). |
| Auth | Полноценный DCR AS; CIMD как authorization server **нет**. Authentik-путь уже без DCR. |
| GraphQL `query_graphql` | Почти ортогонален версии протокола. |

Итог: **SDK впереди приложения.** Перевод gate — не bump crate, а смена
продуктовой модели сессии + dual-protocol к mixed fleet upstreams.

## 4. Почему это сложно (если смотреть на rmcp — не видно)

Интуиция «rmcp 3.1 уже говорит 2026, значит gate почти готов» верна **только
для JSON-RPC типов**. `VmcpServer` не переопределяет
`supported_protocol_versions`, rmcp отдаёт `KNOWN_VERSIONS` включая
`2026-07-28`, `server/discover` есть в дефолтном `ServerHandler`.
`tools/call` / `query_graphql` на одном POST без сессии, скорее всего,
уже проедут.

Сложность в другом: **приложение считает, что у каждого клиента есть
сессия**. 2026 это запрещает. И нельзя просто выключить сессии — Cursor
и наши тесты ещё на handshake.

Ниже — что происходит **сегодня**, без единой строки миграции, если к
`/mcp` подключается modern-клиент.

### 4.1 Recorder и вкладка Sessions становятся пустыми

`capture_mcp` берёт ключ записи из заголовка `Mcp-Session-Id`. На первом
`initialize` заголовка нет — middleware **ждёт** id из response и
дописывает его, иначе C2S **дропается**:

```67:122:crates/vmcp/src/mcp_capture.rs
    // The very first request ("initialize") arrives WITHOUT an `Mcp-Session-Id`
    // header; rmcp generates the id and returns it in the response.
    // ...
            tracing::warn!(
                method = ?req_method,
                "C2S exchange has no session id (initialize failed or broken client); dropping"
            );
```

Клиент 2026-07-28 **никогда** не шлёт и не получает `Mcp-Session-Id`.
Каждый `tools/call` попадает в эту ветку. `Recorder::record` тоже
молчит без пары `(client_id, session_id)`:

```122:128:crates/vmcp-server/src/recorder.rs
        let Some(cid) = ex.client_id.clone() else {
            return;
        };
        let Some(sid) = ex.session_id.clone() else {
            return;
        };
```

Итог для оператора: GraphQL снаружи работает, **вкладка Sessions /
compare / JSONL dump — пустая**, пока ключ не переедет. Это не
«придумать сессию заново». В 2026 id уже есть на первом POST:

- Bearer `client_id` (у vmcp есть);
- `_meta.clientInfo`;
- для живого канала — `subscriptionId` (= JSON-RPC id `subscriptions/listen`).

Чинить recorder = **сменить, откуда берётся sid**, и убрать танец
«подожди header из initialize». Admin UI может остаться
client → sessions → dump. Dual-protocol: два способа завести одну и
ту же вкладку (cookie vs `_meta`/listen).

### 4.2 Push `tools/list_changed` не доходит до modern-клиента

Цепочка сейчас такая:

1. Upstream (postgres) шлёт `notifications/tools/list_changed`.
2. `ForwardingClient` кладёт это на in-process bus.
3. Forwarder идёт по `peers: DashMap<u64, Peer<RoleServer>>`.
4. В map пишут **только** в `on_initialized`.

```97:99:crates/vmcp-server/src/lib.rs
    /// Connected client sessions, captured on `initialized`. The notification
    /// forwarder fans upstream MCP events out to these peers.
    peers: Arc<DashMap<u64, Peer<RoleServer>>>,
```

```604:607:crates/vmcp-server/src/lib.rs
    async fn on_initialized(&self, context: NotificationContext<RoleServer>) {
        let id = self.inner.peer_seq.fetch_add(1, Ordering::Relaxed);
        self.inner.peers.insert(id, context.peer.clone());
    }
```

У 2026 **нет** `notifications/initialized`. Map пустой, пока клиент не
**откроет сессию push** через `subscriptions/listen`. Это тот же
peer-map, другой момент регистрации: `on_initialized` → handler
listen (ack `subscriptionId`, слать `list_changed` в этот SSE, не в
GET `/mcp`).

rmcp 3.1 уже умеет listen на транспорте; vmcp всё ещё кладёт peer
только на legacy handshake. Два клиента на одном `/mcp` (Cursor 2025
+ агент 2026): Cursor получит push, агент — нет, пока не повесим
forwarder на listen.

Это remap точки входа сессии, не новая шина. Объём — ветка
legacy GET SSE + modern listen в одном forwarder.

### 4.3 CI останется зелёным и спрячет поломку

`http_smoke` и почти все integ-тесты ходят через
`handler.serve(transport)`:

```187:188:crates/vmcp/tests/common/mod.rs
    let transport = StreamableHttpClientTransport::from_config(config);
    handler.serve(transport).await.expect("MCP handshake")
```

В rmcp 3.1 `ProtocolVersion::LATEST` = **`2025-11-25`**. Тестовый
клиент сам делает `initialize`, получает `Mcp-Session-Id`, регистрирует
peer. Сценарии 4.1–4.2 **в CI не воспроизводятся**.

Отдельные raw-HTTP тесты (`session_survives_rpc_error`,
`session_fd_burst`) **явно** шлют `2025-11-25` и проверяют resume по
`Last-Event-ID` — фичу, которую 2026 **удаляет**. Пока их не дублируют
modern-путём, «перевели на 2026» = зелёный прогон на старом протоколе.

### 4.4 Dual-protocol: два способа *завести* сессию, не «с сессиями и без»

`StreamableHttpServerConfig::default()` включает
`legacy_session_mode: true`. Это нужно, пока Cursor / vmcp-lite /
скрипты открывают сессию через `initialize`. Значит в одном процессе
живут два входа в один и тот же операторский объект:

| | клиент 2025-11-25 | клиент 2026-07-28 |
| --- | --- | --- |
| Как открыть | `initialize` → cookie `Mcp-Session-Id` | первый POST с `_meta.clientInfo` (+ Bearer) |
| Как открыть push | GET `/mcp` с cookie | POST `subscriptions/listen` → `subscriptionId` |
| Оборванный SSE | `Last-Event-ID` replay (наш патч rmcp, issue #2) | заново открыть listen / новый request id |
| Логи | capability `logging` + `notifications/message` | только если в `_meta` был `logLevel` |
| Idle GC | `LocalSessionManager::close_session` по TTL | закрытие listen-stream; cookie нечего GC |

Каждая строка — ветка «как завели», не отдельный продукт. rmcp
переключает транспорт. Recorder/forwarder ещё ждут только старый вход.

Патч `third_party/rmcp` как раз чинит resume после JSON-RPC error.
Для 2026 он **не должен** работать: спека запрещает redelivery. Выкинуть
патч нельзя, пока жив legacy. Держать его только на
`legacy_session_mode` — отдельная аккуратность, иначе modern-клиент
получит запрещённый replay.

### 4.5 Шлюз — ещё и клиент. Upstream'ы не переедут синхронно

`UpstreamPool` держит `RunningService` после handshake к stdio/HTTP.
`ForwardingClient::get_info()` отдаёт дефолтные capabilities и живёт
в мире `on_tool_list_changed` (старые notifications).

Демо-флот (time, filesystem, presentation) останется на 2025 ещё долго.
Один HTTP-upstream, который включит 2026:

- перестанет слать GET SSE / `resources/subscribe`;
- будет ждать `subscriptions/listen` и `_meta` на каждый RPC;
- `initialize` может ответить `-32601` или потребовать discover.

Пул сейчас **один** lifecycle на всех. Нужен per-upstream probe:
`server/discover` → fallback `initialize`. Иначе «обновили vmcp» =
отвалился один Notion-like MCP, остальные живы. Это клиентская
половина той же dual-модели, не серверная.

### 4.6 Tasks и auth — не bump, но и не бесплатно

Код уже зовёт `get_task` / `cancel_task` и вешает extension id
(SEP-2663). Доки, `instructions` и GraphQL-тексты всё ещё говорят
«опрашивай `tasks/result` / `tasks/list`». `update_task` — stub
(`get` и всё). Клиент 2026, который шлёт `tasks/update` для input,
получит «ок» без эффекта.

DCR трогать не обязательно (deprecated ≠ removed). Но CIMD как AS
vmcp не реализует; Cursor пока на DCR. Это не блокер первой фазы,
это отдельный кусок, если хотим «соответствовать SHOULD» спеки, а не
только RPC.

### 4.7 Что *действительно* дёшево

- Сам `query_graphql` / dynamic schema / registry / hot-reload.
- `server/discover` (дефолт rmcp).
- Заголовки `Mcp-Method` / `Mcp-Name` (rmcp валидирует на 2026).
- `resultType` (rmcp ставит, если negotiated ≥ 2026-07-28).

Поэтому снаружи кажется «уже почти 2026». Ломается не tool call, а
**операторский контур и push**.

## 5. Оценка сложности миграции

**Общая оценка: средняя–высокая (6.5–7 / 10) при dual-protocol.**
Не «сессии удалили, пишем продукт заново». **Два входа в ту же сессию**
(cookie `initialize` vs `_meta` + `subscriptions/listen`), пока Cursor
на 2025. 5.5 / 10, если режем legacy.

Сложность в remap ключа и точки регистрации peer, плюс mixed upstream
client. GraphQL не трогать.

| Подсистема | Сложность | Что трогать |
| ---------- | --------- | ----------- |
| Dual-protocol на `/mcp` | средняя | rmcp уже dual-stack при `legacy_session_mode=true`. Нужны тесты `server/discover` + per-request `_meta` + заголовки SEP-2243. Следить, что `LATEST` не оставит modern-клиентов на 2025-11-25. |
| Sessions / admin / recorder / otel | **средняя** | Не новый объект. Sid: cookie **или** `client_id`+`clientInfo` / `subscriptionId`. Убрать orphan-`initialize` wait в `mcp_capture.rs`. |
| Last-Event-ID patch | средняя | Только legacy path. Modern: клиент заново открывает listen. |
| Notifications | **средняя–высокая** | Тот же peer-map: регистрировать на `subscriptions/listen`, не на `on_initialized`. GET SSE оставить legacy. |
| Upstream pool (клиент) | **высокая** | На upstream нужен `ClientLifecycleMode`: discover → fallback initialize. Смешанный флот (stdio Python 2025-11-25 + HTTP 2026). `ForwardingClient` сейчас живёт в session/initialize мире. |
| Tasks | средняя | Добить SEP-2663: живой `tasks/update`, убрать `tasks/result` из docs/instructions, не рекламировать `tasks/list`. Store SQLite почти ок. |
| Auth | средняя | DCR пока можно оставить (deprecated, не removed). CIMD AS — отдельный кусок. `iss` (SEP-2468), `application_type` (SEP-837), bind credentials к issuer (SEP-2352). |
| Proxy `/mcp-proxy` | средняя | Тот же ServerHandler, плюс list cache hints. |
| GraphQL aggregation | низкая | Внутренний слой. |
| Тесты | высокая по объёму | Почти все HTTP-интеграции завязаны на handshake. Нужна матрица legacy × modern. |
| Клиенты (Cursor, vmcp-lite) | внешняя | Пока хосты на 2025-11-25, **нельзя** выключить legacy. |

### Что *не* надо переписывать с нуля

- GraphQL schema / `query_graphql`
- Registry, sidecars, lock, hot-reload
- OAuth consent UX (можно эволюционировать)
- Admin SPA целиком — вкладка Sessions остаётся; меняется только как
  заводят sid

### Главный риск

Два способа **завести** одну сессию в одном процессе: cookie после
`initialize` и `_meta` + `subscriptions/listen`. rmcp это умеет на
транспорте. Recorder/forwarder ещё ждут только cookie.

Второй риск: **upstream translation**. Клиент 2026, upstream 2025 —
шлюз сам делает `initialize` к upstream и не ждёт cookie от modern-клиента.

## 6. Рекомендуемые фазы (не оценка в днях)

1. **Dual-protocol smoke на `/mcp`:** `server/discover`, `tools/list`/`tools/call`
   с `_meta` (без cookie). Legacy-тесты не ломать. Явно рекламировать
   `2026-07-28` в `supportedVersions`.
2. **Cache hints + `resultType`:** проверить, что rmcp проставляет их на
   list/tool results; дописать если `list_tools` отдаёт сырой struct без
   `ttlMs`.
3. **`subscriptions/listen` = новый вход в push-сессию:** регистрировать
   peer здесь, не в `on_initialized`. Legacy GET SSE остаётся.
4. **Recorder sid remap:** cookie **или** `client_id`+`clientInfo` /
   `subscriptionId`. Убрать wait на `Mcp-Session-Id` из initialize.
   Вкладка Sessions та же.
5. **Upstream client lifecycle:** probe `server/discover`, fallback
   `initialize`. Не форсить 2026 на stdio-демо.
6. **Tasks SEP-2663 complete:** `tasks/update`, docs, instructions
   `query_graphql`/`run_task`.
7. **Auth:** `iss`, `application_type`; CIMD AS — отдельным шагом после
   стабильного dual-protocol.
8. **Не удалять** Last-Event-ID patch, пока есть legacy_session_mode.

Фаза 1 — узкий транспортный срез. Фазы 3–5 — настоящая стоимость: notifications,
observability, mixed upstreams.
